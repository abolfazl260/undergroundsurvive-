# سیستم زمین، طبقات و اتاق‌ها — محدودهٔ MVP زیرزمینی

> تصمیم محصول: [Issue #28](https://github.com/abolfazl260/undergroundsurvive-/issues/28). ساخت‌وساز بازیکن فقط در زیرزمین فعال است؛ توسعهٔ سطحی برای فاز آینده حفظ می‌شود.

## مختصات و قواعد

- شبکهٔ ثابت ۱۴ ستونی با `WORLD.minY=-4` و `WORLD.maxY=2` حفظ شده است. `y < 0` زیرزمین، `y = 0` سطح و `y > 0` آسمان است.
- `constructionPolicy.ts` تنها مرجع تصمیم مجازبودن تراز ساخت و ویرایش است. `UNDERGROUND_ONLY_POLICY` به‌صورت پیش‌فرض `allowSurfaceConstruction: false` دارد. برای گسترش آینده، سیاست `allowSurfaceConstruction: true` قابل تزریق است، ولی آزادسازی عمودی کماکان نیازمند مکانیزم آسانسور است.
- `placement.ts` قبل از قرارگیری، **تمام سلول‌های اتاق** را از نظر تراز و سپس مرز، حفاری، برخورد و تکیه‌گاه بررسی می‌کند؛ `layout.ts` همین قانون را برای ساخت، جابه‌جایی، تخریب و ارتقا اعمال می‌کند.
- اتاق‌های آغازین اکنون در `y=-1` و `y=-2` هستند؛ گلخانهٔ اولیه نیز به زیرزمین منتقل شده است.
- حفاری فقط روی خاک زیرزمین و طبق شرط مجاورت سلول باز انجام می‌شود. قواعد قیمت، تداخل، تکیه‌گاه و ارتقای سطح اتاق‌های زیرزمینی بدون تغییر باقی می‌مانند.
- متد قدیمی `unlockNextFloor()/unlockFloor()` هیچ طبقهٔ مثبت جدیدی باز نمی‌کند. کنترل «بازکردن طبقهٔ +۱» از UI حذف شده؛ تصویر شهر و سطح زمین همچنان دیده می‌شوند.
- گسترش عمودی **صرفاً از طریق آسانسور** در [#2](https://github.com/abolfazl260/undergroundsurvive-/issues/2) پیگیری می‌شود. این ایشیو مکانیزم آسانسور را نمی‌سازد؛ مسیر قبلی بازکردن طبقهٔ بالا را می‌بندد. حفاری مجاور در ترازهای پایین‌تر تا پیاده‌سازی کامل #2 از رفتار فعلی TerrainMap پیروی می‌کند.

## سازگاری با ذخیره‌های قدیمی

- هیچ فیلد Snapshot، `highestFloor` یا مختصات قدیمی حذف نشده؛ `schemaVersion` بدون تغییر مانده است.
- `BuildingLayout.restore` برای **اعتبارسنجی داده‌های تاریخی** از سیاست سازگار با سطح استفاده می‌کند و همچنان تداخل، مرز، حفاری و حمایت ساختاری را بررسی می‌کند.
- ساختمان‌های تاریخی در `y>=0` بدون جابه‌جایی یا حذف دیده می‌شوند، ولی Build/Move/Upgrade/Remove در آن محدوده مجاز نیست. عملیات روی سایر اتاق‌ها همچنان قابل انجام است.
- عملیات‌های پرداختی از نمونهٔ موقت چیدمان استفاده می‌کنند: شکست اعتبارسنجی هیچ سکه‌ای کم نمی‌کند و snapshot ذخیره را تغییر نمی‌دهد.
- بازنشانی پایگاه وضعیت اولیهٔ جدید و فقط زیرزمینی را برمی‌گرداند؛ پاک‌کردن یا مهاجرت خودکار اتاق‌های قدیمی انجام نمی‌شود.

## کنترل‌ها و تست

در وب و نسخهٔ Capacitor یک صحنه/قوانین TypeScript مشترک اجرا می‌شود. در ابزار «ساخت» خانهٔ حفاری‌شدهٔ زیرزمین را لمس کنید؛ در ناحیهٔ سطحی و هوایی ساخت، جابه‌جایی و پیش‌نمایش ساخت غیرفعال‌اند و کلیک نامعتبر پیام بازخورد دارد.

از پوشهٔ `game/`:

```sh
npm install
npm test
npm run build
```

تست‌های `placement.test.ts`، `terrain.test.ts` و `economy.test.ts` سطوح منفی/صفر/مثبت، جلوگیری از هزینهٔ اشتباه، ذخیرهٔ تاریخی و محدودیت API قدیمی را بررسی می‌کنند. قوانین مرورگری باید در اتصال آنلاین بعدی در سمت سرور نیز تکرار شوند.

## پیوست: قانون اتصال اتاق‌ها به آسانسور (#58)

- توسعهٔ افقی جدید فقط با **تماس واقعی ضلع چپ یا راست** به آسانسور متصل یا یک اتاق دارای مسیر پیوسته تا آن امکان‌پذیر است؛ تماس گوشه‌ای، طبقهٔ دیگر و خاک صرفاً حفاری‌شده کافی نیستند.
- `connectivity.ts` گراف اتصال را مستقل از Phaser و با ریشهٔ قطعات متصل آسانسور محاسبه می‌کند. تمام عملیات ساخت/جابجایی/تخریب در دامنهٔ ساختمان همین قانون را بررسی می‌کنند؛ حذف یا جابجایی اتاق واسط که اتاق دیگری را قطع کند نامعتبر است.
- چهار اتاق آغازین برای بازی **جدید** به صورت پیوسته به آسانسور چیده می‌شوند. ذخیره‌های تاریخی معتبر که اتاق جداافتاده دارند **بدون حذف، جابجایی خودکار یا دستکاری مختصات** بارگذاری می‌شوند؛ پیام هشدار نمایش داده می‌شود، `disconnectedRoomIds` برای تشخیص قابل استفاده است و بازیکن می‌تواند آن‌ها را به شبکه متصل کند. عملیات جدید حق ندارد اتاق قبلاً متصل را جدا کند.
- اعتبارسنجی بازگردانی با `validateFootprint` (بررسی هندسی مستقل از ترتیب snapshot) انجام می‌شود تا ذخیره‌های قدیمی به علت قوانین تازه حذف نشوند. اعتبارسنجی `validatePlacement` فقط برای عملیات تازه، اتصال را الزامی می‌کند.
- پیش‌نمایش سبز موقعیت‌های قابل ساخت را روی نقشه مشخص می‌کند؛ پیش‌نمایش قرمزِ محل نامعتبر دلیل رد اتصال/هزینه/تداخل را نشان می‌دهد. قانون در منطق مشترک وب و موبایل اعمال می‌شود؛ در صورت اضافه‌شدن API آنلاین، **همین اعتبارسنجی باید در سرور نیز اجرا شود** و کلاینت قابل اعتماد نیست.
