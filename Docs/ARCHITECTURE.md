# معماری فنی Underground Survive — Web-First

> وضعیت: تصمیم معماری برای شروع توسعه — 2026-10-30  
> این سند طراحی است؛ وجود این فایل به معنی پیاده‌سازی زیرساخت نیست.

## هدف

یک هستهٔ دوبعدی مشترک برای **وب (مرورگر/PWA)، Android و iOS** با ماژول‌های مستقل، هزینهٔ آغازین و سربار عملیاتی کم؛ در صورت رشد محصول، امکان جداسازی سرویس‌های پرترافیک حفظ شود.

## پشتهٔ انتخابی

| لایه | ابزار | مسئولیت |
| --- | --- | --- |
| بازی | Phaser + TypeScript | رندر دوبعدی، ورودی لمسی/ماوس، انیمیشن و صحنه‌ها |
| ابزار ساخت | Vite + TypeScript | توسعهٔ محلی و بیلد وب |
| نسخهٔ وب | Static Hosting + PWA | دسترسی از مرورگر و نصب‌پذیری احتمالی |
| نسخهٔ Android و iOS | Capacitor | بسته‌بندی برنامهٔ وب در WebView و دسترسی کنترل‌شده به APIهای بومی |
| بک‌اند آنلاین | Supabase | Auth، PostgreSQL، Edge Functions، Storage و Realtime فقط در صورت نیاز |
| کنترل نسخه/CI | GitHub + GitHub Actions | تست، بررسی تغییرات و بیلد |

**وب اولین خروجی اجرایی است**؛ برای موبایل از همان کد بازی استفاده می‌شود. انتشار و تأیید فروشگاه‌ها نیازمند تست و بسته‌بندی جداگانه است. بازی روی موبایل در WebView اجرا می‌شود؛ تست کارایی روی دستگاه واقعی الزامی است.

## اصل جداسازی ماژول‌ها

ماژول‌ها **قابلیت‌محور** تعریف می‌شوند؛ هر ماژول منطق خالص، موارد استفاده، رابط‌های ارتباطی و اجزای نمایشی خود را در صورت نیاز دارد. اتصال مستقیم ماژول‌ها به دیتابیس یا کدهای داخلی یکدیگر ممنوع است.

| ماژول | مالکیت |
| --- | --- |
| `world` | Grid، خانه‌ها، طبقات، حفاری و مختصات |
| `building` | قواعد قرارگیری، ساخت، تخریب، ارتقا و چیدمان اتاق |
| `economy` | موجودی سکه، محاسبهٔ قیمت و تراکنش‌های معتبر |
| `characters` | آدمک‌ها، انیمیشن و حرکت |
| `survivors` | تخصص‌ها و تخصیص ساکنان |
| `missions` | اهداف، وضعیت و پاداش مأموریت |
| `defense` | دیوار، برج، تله و استحکامات |
| `combat` | محاسبه و ثبت حمله، مستقل از نمایش |
| `alliances` | اتحادها، عضویت و روابط بازیکنان |
| `cosmetics` | تعریف، مالکیت و فعال‌سازی اسکین |
| `identity` | نشست، ورود و خروج بازیکن |

**قواعد:** Phaser فقط نمایش را انجام می‌دهد؛ قوانین جای‌گذاری اتاق و قیمت‌ها در کد مستقل از Phaser تعریف شوند. ماژول‌ها از `contracts` مشترک و APIهای عمومی یکدیگر استفاده کنند. رویدادهای داخلی مثل `room-upgraded` برای مأموریت‌ها قابل استفاده‌اند، اما منبع حقیقت رویدادهای اقتصادی سرور است.

## طراحی سیستم ساخت‌وساز

- مختصات صحیح Grid با `x` و `y`؛ قرارداد اولیه: سطح زمین `y=0`، بالای زمین مثبت و زیرزمین منفی.
- اتاق یک موجودیت داده‌ای مستقل از Sprite است: `id, typeId, x, y, width, height, level`.
- قوانین قبل از ساخت: محدودهٔ آزادشده، عدم هم‌پوشانی، وضعیت حفاری، پیش‌نیاز و هزینهٔ معتبر.
- کلاینت پیش‌نمایش سریع می‌دهد، اما سرور تمام قواعد حساس را دوباره اعتبارسنجی می‌کند.
- وضعیت Grid و اتاق‌ها به‌شکل داده ذخیره شوند، نه از روی Phaser GameObject.
- برای جهان‌های بزرگ، رندر فقط قسمت قابل مشاهده و بارگذاری تدریجی در نظر گرفته شود.

## عملیات آنلاین و امنیت

Supabase کلاینت برای احراز هویت و خواندن داده‌های مجاز است؛ **امنیت سکه، ساخت اتاق، ارتقا، پاداش مأموریت، مالکیت اسکین و نتیجهٔ نبرد نباید به کد مرورگر سپرده شود.**

برای فرمان‌های حساس از **Postgres RPC تراکنشی** با محدودیت‌های صریح و در صورت نیاز **Edge Functions** استفاده شود:
1. بررسی هویت و مالکیت پایگاه.
2. اعتبارسنجی درخواست، هزینه، موقعیت و پیش‌نیازها در سرور.
3. اجرای اتمیک کسر سکه + ثبت اتاق با یک تراکنش.
4. استفاده از `operation_id` برای جلوگیری از اجرای مجدد و `base_version` برای کنترل تعارض.
5. ثبت تاریخچهٔ تراکنش و بازگرداندن وضعیت معتبر به کلاینت.
6. فعال‌سازی RLS در جداول قابل دسترسی مستقیم و اعمال حداقل دسترسی؛ کلیدهای محرمانه هرگز در کلاینت قرار نگیرند.

برای ساخت و ارتقای اتاق، HTTP/RPC کافی است. Realtime فقط زمانی اضافه شود که اعلان، نمایش وضعیت اتحاد یا پیام‌رسانی واقعاً به آن نیاز داشته باشد. برای PvP نسخهٔ اول **نبرد غیرهم‌زمان** پیشنهاد می‌شود تا نیاز به سرور مبارزهٔ realtime از ابتدا ایجاد نشود.

### داده‌های اصلی

`profiles`, `bases`, `terrain_cells`, `rooms`, `survivors`, `wallets`, `wallet_transactions`, `missions`, `player_missions`, `defenses`, `alliances`, `alliance_members`, `battles`, `owned_skins`, `verified_purchases`.

این‌ها جدول‌های پیشنهادی‌اند. هنگام پیاده‌سازی، مالکیت، RLS، Index، نسخه‌بندی اسکیمای داده و محدودیت‌های یکتایی لازم است.

## پرداخت و اسکین

- اسکین‌ها ترجیحاً فقط ظاهری باشند.
- مالکیت خرید در سرور ذخیره شود؛ تراکنش‌ها باید یکتا و قابل بازیابی باشند.
- برای Android/iOS پرداخت با سازوکار معتبر هر فروشگاه انجام شود؛ برای وب پرداخت جداگانه با رعایت قوانین پلتفرم‌ها بررسی شود.
- تأیید خرید فقط با پیام موفقیت کلاینت انجام نشود؛ سرور باید رسید/تراکنش را اعتبارسنجی کند.
- انتخاب ارائه‌دهندهٔ پرداخت وب و جزئیات قوانین فروشگاه‌ها پیش از توسعهٔ P5 نهایی شود.

## تست و استقرار

- تست واحد TypeScript برای Grid، قوانین برخورد، هزینه‌ها و مسیرها؛ تست مرورگر و تست عملکرد روی گوشی‌های ضعیف.
- تست یکپارچهٔ عملیات ساخت/ارتقا در برابر درخواست هم‌زمان و تکراری.
- محیط‌های جداگانهٔ Development و Production در Supabase؛ تغییر دیتابیس فقط با Migration.
- نسخهٔ وب با CI قابل انتشار باشد و بیلد Android/iOS به همان نسخهٔ کد اشاره کند.
- از ابتدا اندازهٔ Bundle، بارگذاری Asset و مصرف حافظه در WebView کنترل شود.

## محدودهٔ فازها

- **P0:** پروژهٔ Phaser/TypeScript + Vite، پیش‌نمایش وب، ساختار ماژول‌ها، Supabase Auth و ذخیرهٔ امن آزمایشی.
- **P1:** Grid، اتاق‌ها، حفاری، طبقات، چیدمان، ارتقا، سکه و حرکت آدمک‌ها؛ نسخهٔ وب قابل‌بازی.
- **P2:** تخصص‌ها، تأسیسات، مأموریت‌ها؛ نخستین بیلدهای تست Android و iOS با Capacitor.
- **P3:** دفاع و شبیه‌سازی حمله.
- **P4:** اتحاد و PvP غیرهم‌زمان (در صورت نیاز پس از آزمون، realtime).
- **P5:** اسکین، پرداخت و آماده‌سازی انتشار عمومی موبایل.
