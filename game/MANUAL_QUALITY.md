# آزمایش‌های یکپارچه و دروازهٔ انتشار دستی Android

## اصل اجرا

تست‌های گسترده و هر دو نوع خروجی Android صرفاً **با اقدام صریح مالک** اجرا می‌شوند؛ هیچ `push`، `pull_request`، زمان‌بندی یا انتشار خودکاری برای این مرحله تعریف نشده است. بررسی‌های سریع وب که از قبل در مخزن وجود داشتند، مستقل باقی می‌مانند و به‌صورت خودکار اجرا می‌شوند.

**توجه:** تست‌های Browser در Chromium با شبیه‌سازی اندازه و تاچ موبایل اجرا می‌شوند؛ جای تست APK روی دستگاه واقعی را نمی‌گیرند. همچنین یک APK تولیدشده به معنای انتشار در Play Store نیست.

## گزینه‌های موجود در GitHub Actions

| Workflow دستی | کاربرد | تست‌ها / خروجی |
| --- | --- | --- |
| `Manual game quality tests` | اجرای موردی، بدون تولید APK | `integration` فقط یکپارچه؛ `full` یکپارچه و Soak؛ `release-gate` علاوه بر آن بررسی مرزهای ذخیره و دو بیلد clean؛ گزینهٔ مستقل تست مرورگر |
| `Capacitor Android checks` | آزمایش یا ساخت Debug APK | `build_apk` اختیاری، `run_extended_quality` برای شبیه‌سازی طولانی و لمس، `strict_reproducibility` برای دو نصب/بیلد پاک |
| `Build signed Android release (manual only)` | تولید **امضاشده** APK/AAB | الزام به lockfile، دو `npm ci` و هش خروجی یکسان، تست‌های کامل و مرورگر، سپس امضای Android و کنترل امضا |
| `Generate npm lockfile (manual only)` | تولید قفل نسخهٔ وابستگی‌ها | `package-lock.json` به‌عنوان Artifact برای بازبینی؛ **هیچ commit خودکاری** انجام نمی‌شود |

### نحوهٔ استفاده

در صفحهٔ Actions مخزن، Workflow دلخواه را انتخاب کنید، `Run workflow` را بزنید، برنچ را تعیین کنید و ورودی‌ها را تنظیم کنید. همهٔ نتایج در همان Run و مدارک تصویری/هش‌ها در قسمت Artifacts ثبت می‌شوند.

برای کار روزمره نیازی به اجرای مجموعهٔ گسترده نیست. قبل از انتشار عمومی ابتدا `Manual game quality tests` را با `suite=release-gate` اجرا کنید و سپس Workflow نسخهٔ امضاشده را به‌صورت دستی روی `main` اجرا کنید؛ خود آن Workflow نیز الزاماً همهٔ کنترل‌های اصلی را از نو اجرا می‌کند.

## پوشش آزمایش‌ها

### ۱. یکپارچه‌سازی و یکسانی شبیه‌سازی

- ساخت اتاق با پرداخت واقعی، دریافت پاداش و اجرای چرخهٔ اقتصاد.
- Serialize/Restore کامل بازی و مقایسهٔ Snapshot پس از بازیابی.
- یکسانی نتیجهٔ دو بازی با شرایط اولیه و Tickهای برابر.
- محدودکردن زمان جبران‌شده بعد از Suspend دستگاه به حداکثر ۶۰ ثانیه.
- ردکردن ذخیره‌هایی که پول جعلی یا اتاق‌های دارای تداخل دارند.

اجرا از `game/`: `npm run quality:integration`.

### ۲. بازی طولانی (Soak)

- پیشروی بازی در گام‌های ۶۰ ثانیه‌ای بدون صبرکردن زمان واقعی.
- کنترل مثبت و محدودبودن مقادیر منابع و ذخیرهٔ هر ۳۰ دقیقهٔ شبیه‌سازی‌شده.
- سریال‌سازی و بازیابی دوباره و بررسی ثبات وضعیت.
- مدت پیش‌فرض: **۴ ساعت زمان فعال شبیه‌سازی‌شده**؛ برای اجرای دستی `GAME_SOAK_HOURS=12 npm run quality:soak` (۱ تا ۴۸ ساعت).

### ۳. مقاومت در برابر خرابی ذخیره

- بازیابی ذخیرهٔ سالم از `localStorage`.
- ردکردن JSON ناقص و رکورد تغییر‌داده‌شده، بدون Crash.
- بررسی ثبت بایت‌های خراب در کلید `underground-survive:recovery`.
- شناسایی خطای مجوز یا سهمیهٔ ذخیره‌سازی به‌جای گزارش موفقیت کاذب.
- آزمون مرورگری: بازی، رفرش، مقایسهٔ سکه، تزریق ذخیرهٔ خراب، رفرش و بررسی سالم‌ماندن صحنه.

**محدودیت فعلی:** نگهداری دادهٔ خراب به‌معنی بازیابی پیشرفت قبلی نیست؛ طراحی پشتیبان معتبر و مهاجرت خودکار یک کار توسعه‌ای جداگانه است.

### ۴. تاچ واقعی مرورگر و واکنش‌گرایی

- Playwright Chromium با Touch واقعی (نه تنها dispatch کردن click).
- اندازه‌ها: `320×568`، `390×844`، `768×1024` و `844×390`.
- کنترل حداقل ابعاد دکمه‌ها و لمس پنل ساخت/ابزارها، برق، زوم، دستاوردها، منوی توقف و لغو عملیات تخریبی.
- ذخیره/بازیابی و دادهٔ خراب روی چیدمان Portrait و Landscape.
- تصاویر Evidence ذخیره می‌شوند. **این آزمایش جایگزین لمس دو انگشتی یا تست روی Android WebView واقعی نیست.**

اجرا پس از نصب Playwright و راه‌اندازی `npm run preview`: `npm run quality:browser`.

### ۵. تکرارپذیری بیلد و صدور Release

- الزام به وجود `game/package-lock.json` و تطبیق Dependencyها با `package.json`.
- دو نصب مستقل با `npm ci`، دو بیلد Vite و مقایسهٔ SHA-256 هر فایل نهایی.
- ذخیرهٔ `quality-evidence/reproducibility.json` شامل نام فایل‌ها، هش‌ها و هش lockfile.
- اجرای این کنترل قبل از ساخت APK/AAB امضاشده؛ شکست آن کل فرایند انتشار را متوقف می‌کند.
- پس از ساخت، امضای APK با `apksigner` و AAB با `jarsigner` بررسی و فهرست SHA256SUMS تولید می‌شود.

این کنترل یکسانی باندل **وب** را تأیید می‌کند، نه لزوماً byte-identical بودن APK/AAB در دو Gradle build مستقل.

## مسدودکننده‌های شناخته‌شدهٔ انتشار

تست `npm run quality:limits` عمداً برای دو نقیصهٔ فعلی **Fail** خواهد شد تا نسخهٔ انتشار با ریسک شناخته‌شده تولید نشود:

1. `lifeSupport.ticks` پس از عبور از ۱۰۰٬۰۰۰ چرخه در بازیابی Snapshot رد می‌شود.
2. `Wallet.restore` ذخیره‌ای با بیش از ۵٬۰۰۰ تراکنش را نمی‌پذیرد، در حالی که کد ثبت تراکنش‌ها رشد می‌کند.

ابتدا باید سیاست ذخیره‌سازی بلندمدت و سازگاری نسخه‌های قبلی اصلاح شود. تا آن زمان می‌توان Debug APK را برای تست ساخت، اما Release با کنترل سخت‌گیرانه مسدود می‌ماند.

همچنین **اکنون package-lock.json در مخزن ثبت نشده** است. Workflow `Generate npm lockfile (manual only)` را اجرا، فایل Artifact آن را بررسی و در یک PR مستقل به مخزن اضافه کنید. بدون این فایل، Release Gate به‌درستی Fail می‌شود.

## چک‌لیست آزمایش APK روی گوشی

بعد از ساخت Debug یا نسخهٔ امضاشده روی حداقل یک گوشی واقعی این موارد را دستی بررسی کنید: نصب آفلاین؛ شروع سرد؛ رفتن به پس‌زمینه و برگشت؛ بسته‌شدن اجباری و بازیابی ذخیره؛ Back بومی؛ ناچ/Safe area؛ زوم دو‌انگشتی؛ Portrait و Landscape؛ فارسی و انگلیسی؛ صدای غیرفعال؛ قطع آب و برق؛ ساخت، ارتقا، حذف و تخصیص نیرو؛ دمای دستگاه، حافظه و افت فریم؛ و نصب نسخهٔ بعدی روی نسخهٔ قبلی بدون ازدست‌رفتن پیشرفت.

هیچ Workflow موجودی به Play Store انتشار نمی‌دهد و هیچ تست یا بیلد iOS در این برنامه فعال نشده است.
